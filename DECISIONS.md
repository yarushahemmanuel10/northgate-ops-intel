## D-001: SLA timers use elapsed hours, not business hours
- **Choice:** Measure SLA response and resolution times in elapsed wall-clock hours.
- **Alternatives:** Business hours only (e.g. 08:00–18:00 Mon–Fri, excluding bank holidays); P1 on 24/7 and P2–P4 on business hours.
- **Reason:** Keeps the KPI logic simple and easy to verify by hand within the time available. Business-hours calendars are a well-understood extension and are listed as future work. Breach rates will look slightly worse than under a business-hours rule.

## D-002: Fixed as-of date of 30 September 2026
- **Choice:** Treat all data as extracted at the end of 30 September 2026 and use that moment for every time-relative calculation (open tickets, ticket age, next 90 days, trend windows). Definitions in `docs/01_business_processes.md` §1.7.
- **Alternatives:** Use the real current date at run time; use the latest timestamp found in the data.
- **Reason:** Results must be identical every time the code runs, including during interviews months later. The real date would make "next 90 days" drift out of the data window; the latest timestamp varies between sources and with injected bad dates.

## D-003: One revenue source per business line
- **Choice:** BL1, BL3, BL4 revenue modelled from CRM contract lines (annual value ÷ 12 per active month); BL2 from telecoms bills only; BL5 from shop orders only. The CRM records value per business line so this split is possible.
- **Alternatives:** Use CRM contract value for all lines; add CRM BL2 value to telecoms bills; leave BL1/BL3/BL4 out of revenue.
- **Reason:** Each pound is counted once. Billing is the record of what was actually charged for telecoms, so the CRM BL2 value is only used for the BQ-13 check. Lines with no transaction source are included but labelled "modelled" rather than presented as measured.

## D-004: Keep response SLA by adding `first_responded_at`
- **Choice:** Add a `first_responded_at` field to the helpdesk export and measure response SLA as well as resolution SLA.
- **Alternatives:** Drop response SLA and report resolution SLA only.
- **Reason:** Response time is a standard MSP service level and appears in the fact sheet's SLA table. Tickets missing the field are excluded from response compliance and counted separately rather than guessed.

## D-005: Python 3.12, uv, exact pins and a committed lock file
- **Choice:** Python 3.12 managed by `uv`. Direct dependencies pinned to exact versions (`==`) in `pyproject.toml`; the full resolved tree, including transitive packages, committed in `uv.lock`. New packages are added per phase, each named in the step that adds it.
- **Alternatives:** pip with `requirements.txt`; lower-bound pins (`>=`); conda; Python 3.11 or 3.13.
- **Reason:** Anyone cloning the repo gets the same versions with `uv sync`, which is needed for every figure to be reproducible. 3.12 meets the brief's 3.11+ requirement and is widely supported by the libraries planned (sentence-transformers, ChromaDB, Prefect, Streamlit). Exact pins in `pyproject.toml` make the versions visible without reading the lock file.
- **Note:** the build environment used during development keeps its virtual environment in `.venv-linux/` (ignored by git), so a local `uv sync` on macOS can create its own `.venv/` without clashing.

## D-006: Fictional company names, with honest wording about real companies
- **Choice:** Customer names are built from generic word lists (North East place words, trade words, legal suffixes, and surnames from a seeded Faker instance). A small blocklist in `config/generator.yaml` rejects names containing specific words (Northgate, real brand names, public-sector words). Every generated file is labelled as synthetic and fictional.
- **What is not claimed:** names were not checked against Companies House or any register of real companies, which cannot be done offline. Because the names are built from common words, some may coincidentally match real businesses. Documents say "fictional" and never "verified not to exist".
- **Alternatives:** an online check against Companies House (needs network and an API key, and still can't rule out unregistered businesses); obviously artificial names such as "Company 017" (removes the realistic name messiness that entity resolution must handle).
- **Reason:** Realistic names are needed for realistic matching problems; honest wording keeps the claim to what can be verified.
- **The provider's own name:** "Northgate IT Services Ltd" is a made-up company name and has no connection to any real company called Northgate, including Northgate plc in Darlington.
- **Name patterns:** place + trade (about 65%), surname + trade (20%), two surnames + trade (10%), place + trade + "Group Ltd" (5%). "& Co" is only used after a surname, and only in sectors where it reads naturally.

## D-007: Uptake and contract values calibrated to the target revenue mix
- **Choice:** Each business line is taken by exactly `round(rate × 120)` customers (plus a few forced so at-risk customers have the lines their pattern needs). Annual value ranges per line live in `config/generator.yaml` and were calibrated on the average of seeds 1–50, not on the project seed (`python -m generator.customers --calibrate 1 50`).
- **Result for the project seed** (`python -m generator.customers`): BL1 +0.7, BL2 −1.7, BL3 +0.1, BL4 −0.1, BL5 +0.9 percentage points from target.
- **Held-out seeds 101–130** (`python -m generator.customers --spread 101 130`), not used for calibration: every line within −2.8 to +2.7 points of target.
- **Tests:** the project seed and held-out seeds 101–110 must each be within ±3 points of every target.
- **How the design got here (exploratory runs of earlier code, not reproducible from the current version):** with independent random uptake per customer and ranges tuned on the project seed alone, the project seed hit every target exactly but seeds 1–20 put BL2 between +2.1 and +13.5 points off. Calibrating on the average of seeds 1–50 but keeping random uptake still left held-out seeds between −7.0 and +5.0 points, and the project seed's BL2 at −6.1. Fixing uptake counts removed most of that variation.
- **Caveat:** BL2 and BL5 figures at this stage are stand-ins (CRM BL2 value and shop budgets). Real BL2 and BL5 revenue is measured after the billing and shop generators run.
- **Reason:** The mix should be near target because of the design, not because of a lucky seed.

## D-008: One independent random stream per concern
- **Choice:** `make_rngs(seed)` creates one numpy Generator and one Faker instance from the project seed. Inside the generator, the numpy Generator is split with `Generator.spawn()` into child streams for names, roles and dates, line uptake and shop budgets, and contract lines. Faker is used only for names.
- **Alternatives:** draw everything from one stream in sequence.
- **Reason:** With one shared stream, any change to how names are drawn shifts every later draw, so a cosmetic change to names would silently change roles, dates and revenue. Separate streams keep each part stable when another part changes (tested in `test_substreams_are_independent`). While building this, a single shared stream also showed that `permutation()` results barely changed when only a few earlier draws changed, which made the coupling between parts hard to reason about. Separate streams avoid relying on that behaviour.
- **Per module:** each later generator module draws from its own named stream, `named_stream(seed, name)` in `generator/streams.py` (seed plus a CRC32 of the module name). The helpdesk generator uses `"helpdesk"`; the knowledge base will use its own, so adding KB links later never changes any ticket.

## D-009: Shop-only customers are CRM accounts; "customer since" replaces "first contract start"
- **Choice:** Customers who buy only from the shop (BL5) appear on the CRM Accounts sheet like every other customer, with no rows on the Contract Lines sheet. The Accounts sheet carries `Customer Since`: the date the customer relationship began (for shop-only customers, when their account was opened). Contract dates live only on the Contract Lines sheet. The ground-truth column is renamed from `first_contract_start` to `customer_since` to match.
- **Basis in the fact sheet:** onboarding (`docs/01_business_processes.md` §2.1) starts with the account manager adding every new customer to the CRM workbook, and the CRM is the master list of canonical customers (`02` §1.3). A customer missing from the master list could never be resolved.
- **Consequence:** BQ-16 (onboarding) uses each customer's earliest contract line start, so shop-only customers, who are not onboarded through support, are excluded from it.
- **Alternatives:** leave shop-only customers out of the CRM (breaks the master-list rule and makes their shop orders unmatchable); give them a dummy BL5 contract line (invents a contract that doesn't exist and contradicts D-003).

## D-010: Same synthetic-data marker on every data sheet and CSV
- **Choice:** Row 1 of each data sheet in the CRM workbook holds the same `# SYNTHETIC DATA ...` marker as the first line of the CSV files; headers are on row 2. The workbook also has a README sheet.
- **Alternatives:** README sheet only, with headers on row 1 as in a typical export.
- **Reason:** Every file and every sheet stays labelled even if copied out on its own, and all connectors handle the marker the same way (skip one row). The cost is that the workbook is slightly less like a real export, which is acceptable because realism is not the point of the marker.
- **Determinism:** the workbook's created and modified dates and the zip entry timestamps are fixed at 2026-09-30 18:00, so the same seed always produces a byte-identical file.

## D-011: Helpdesk ticket rules
- **Who raises tickets:** only customers with a BL1 (managed IT support) contract line, between the line's start (or the window start) and its end. The fact sheet ties support tickets and SLAs to BL1 (§1.3, §2.2; `02` §1.2), so telecoms-only customers raise none.
- **Exact breach counts:** for each priority, exactly `round(rate × n)` tickets are generated as resolution breaches, and `round(6% × n)` overall as response breaches. With independent random draws, the project seed came out at P1 1.9% against a 10% target (1 breach in 53 closed tickets) and P3 12.5% against 15%, although averages over seeds 1–10 matched the targets. Exact counts make the generated rates match the design, so later KPI tests check the pipeline, not sampling luck. Rates on closed tickets still differ slightly from target because tickets still open at the as-of date are excluded.
- **Open tickets:** tickets whose closing time would fall after the as-of moment are open; further P3/P4 tickets opened in September 2026 (not from closed customers) are left open to reach exactly 40, representing a backlog.
- **At-risk rise rule (BQ-06):** Jul–Sep 2026 tickets at least 2 × Apr–Jun 2026 and at least 8. At-risk customers are generated to meet it. The first setting tried (1.5 × and at least 6, with more variation in ticket rates between customers) was met by chance by 6 healthy customers on the project seed; sweeping settings over 13 seeds, 2 × / at least 8 with rate shape 8 averaged 0.62 healthy customers per seed and 1 on the project seed. Healthy customers are never edited to avoid the rule: the remaining chance matches are realistic false positives.
- **Text:** descriptions and resolution notes come from fixed, hand-written templates per topic (`generator/ticket_text.py`), filled with seeded slot values. No LLM is used. Each ticket's `topic_id` is kept in the ground truth for linking to knowledge base articles in a later step.
- **Staff names:** agent and account manager surnames are reserved: no customer name contains them, and customer contact names added later must not either, so masking can tell staff and customer-side people apart.

## D-012: Telecoms contracts and bills
- **VAT:** all money amounts in the project exclude VAT: CRM contract values, telecoms bills and (later) shop orders. B2B prices and contract values are normally quoted ex VAT, and one basis everywhere means totals can be compared without conversion.
- **Bill timing:** the bill for month M is dated the last day of M and covers that month's line rental and calls. With the as-of moment at the end of 30 September 2026 (D-002), the September 2026 bill has been issued and is in the export. No bill exists for a month before the contract starts, on or after a closed customer's closing date, or outside the data window. First and last part-months are prorated by days.
- **Amounts:** a BL2 contract's annual value is split into a fixed monthly line rental (65%) and variable call charges (35% on average, gamma-distributed, never negative). Twelve full months of bills come within 10% of the CRM annual value (tested). Realised BL2 revenue over the window is £1,083,532 against the D-007 stand-in of £1,100,700 (−1.6%).
- **At-risk spend fall:** line rental stays fixed per contract, so the fall comes from call charges, which drop by 55–75% from July 2026 for at-risk BL2 customers. Rule: Jul–Sep 2026 bills at most 0.85 × Apr–Jun 2026. All 9 at-risk BL2 customers meet it without further adjustment; 0 of 49 active healthy BL2 customers meet it by chance. Closed customers are outside BQ-06 (active customers only) because their bills stop at closure.
- **Name style and QI-01:** the billing system writes every name upper case, without the legal suffix, cut to 20 characters. That is a system convention, so it applies to 100% of telecoms names in the clean data and counts as QI-01 (names differ from the CRM). The config's former telecoms rate of 90% is replaced by `telecoms_extra: 0.15`: the share of names that step 1.9 additionally gives a human variant (typo, abbreviation) before the system style, so mess is not stacked on mess.
- **Clean one-to-one:** exactly one telecoms account and contract per CRM BL2 contract line, with end dates equal to the CRM end date (closed customers) or renewal date. QI-11 (lines with no account, accounts with no line, mismatched end dates) is added in step 1.9 by editing the raw telecoms files and recording each change against `data/ground_truth/telecoms_accounts.csv` and `known_issues.csv`, without regenerating customers, tickets or bills.
- **Own stream:** `named_stream(seed, "telecoms")`, split into account numbering, call charges and at-risk reductions.

## D-013: Shop orders and the mock shop API
- **Orders:** customers who use the shop (BL5) order from `customer_since` (or the window start) until the day before closing (or the as-of date), mostly in working hours. Order counts follow each customer's annual shop budget divided by the expected order value (£240.47 from the catalogue in `config/generator.yaml`), giving 3,017 orders. Products are generic, prices exclude VAT (D-012). Promised dates are 2–7 days after the order and deliveries 1–9 days after; deliveries after the as-of date are left empty. All orders are clean until step 1.9 (no cancellations, refunds or duplicates). Realised BL5 revenue is £734,394 against the D-007 stand-in of £750,650 (−2.2%).
- **Second shop accounts:** 8 customers have a second shop account: one healthy "account switcher" (all ordering moves to the second account from July 2026), one at-risk customer, and six others. The switcher is the false-alarm trap described in `02` §1.7.
- **At-risk shop fall:** from July 2026 each at-risk customer's orders are thinned at a rate drawn from 75–95%; rule: combined Jul–Sep 2026 shop spend across all their accounts at most 0.4 × Apr–Jun 2026. Realised: 6 of the 10 at-risk customers place no shop orders at all in Jul–Sep 2026 (ACC-0004, 0007, 0027, 0050, 0082, 0115); the other 4 have ratios between 0.07 and 0.20. One (ACC-0027) needed its largest Jul–Sep order dropped to meet the rule. Six customers stopping completely is a strong, possibly unrealistically clean signal; the thinning range can be softened later if the at-risk score looks too easy.
- **Chance matches are high for the shop on its own:** 10 of 81 active healthy customers meet the shop rule by chance on combined spend, and 13 of 88 healthy shop accounts per account (including the switcher's first account, as intended). Shop spend is lumpy: about five orders a quarter, some of them laptops. Settings were swept over six seeds: even a 0.25 ratio with a £1,000 minimum left 3–11 healthy customers flagged, so no single-source shop threshold is reliable at this order volume. Healthy customers were not edited to avoid the rule.
- **Consequence for BQ-06:** the at-risk pattern is "rising tickets **and** at least one falling spend source". On the project seed all 10 at-risk customers match it and 1 of 105 active healthy customers (ACC-0076) matches by chance. Phase 4's at-risk score must combine signals rather than flag on shop spend alone.
- **API:** FastAPI app in `shop_api/app.py`, run with `uvicorn shop_api.app:app --host 127.0.0.1 --port 8765` (localhost only). `GET /orders` returns pages sorted by order ID, filters on the order date inclusive at both ends, returns an empty list past the last page and 422 for invalid parameters (including `from_date` after `to_date`). Every response carries `"synthetic": true`. Tests use FastAPI's test client, so no server runs during tests.

## D-014: Knowledge base content and ticket links
- **Static, hand-written content:** 50 Markdown documents in `knowledge_base/` (44 articles, 6 policies), written once and committed as source content, not generated at run time. No LLM was used. Body length: min 210, median 273, max 469 words (`python -m generator.kb`).
- **Structure:** one current article per ticket topic (KB-0001 to KB-0025), one superseded article (KB-0026), four near-duplicates of topic articles by a different team (KB-0027 to KB-0030), 14 general guides (KB-0031 to KB-0044, some listing several topics), and 6 policies (KB-0045 to KB-0050).
- **No invented numbers:** every number in any KB document appears in the fact sheet (§1.3 SLA targets, §1.9 service standards, added before the policies were written). `tests/test_kb.py` checks every document, and checks the SLA policy table against `config/generator.yaml`.
- **Superseded article that conflicts:** KB-0026 (old) told customers to report a site-wide outage by email and restart the router; KB-0015, which replaced it on 2025-11-03, says outages are phoned in and the router must not be restarted. Retrieval must prefer KB-0015.
- **Near-duplicates:** three pairs agree in substance and differ only in author and wording (KB-0005/0027, KB-0012/0028, KB-0001/0029). One pair disagrees on a detail (KB-0008/0030: whether the user or an agent completes registration of a new MFA phone); both are marked current. Evaluation questions should avoid that detail or only accept answers that note the conflict. Recorded in `knowledge_base/_meta.yaml`.
- **No personal data:** authors are teams or roles, not people; no customer names, staff names, email addresses or phone numbers appear (tested).
- **Ticket links:** exactly 45% of tickets (691 of 1,535) link to an article that covers the ticket's topic, existed when the ticket was opened and was not yet superseded; articles for one topic are three times as likely to be chosen as general guides. QI-09: 15 tickets on the internet-outage topic opened after 2025-11-03 still link to KB-0026. Links run on their own named stream (`"kb_links"`); a test confirms every other ticket column is unchanged. The ground truth keeps each true link and an outdated flag, so step 1.9 can remove 40% of links from the raw file (QI-08) without losing them.

## D-015: How the deliberate quality problems are injected and recorded
- **Approach:** `generator/messiness.py` builds the clean sources in memory (exactly what the generators write), applies the quality problems, and writes the messy files over `data/raw/`. No source is regenerated.
- **Answer key:** every change is one log entry in `data/ground_truth/known_issues.csv`: a changed cell, an added row or a removed row, with the row's position at the time and typed JSON for the old and new values (dates, numbers, whole rows and order lines). Undoing the entries newest first restores the clean files byte for byte; `test_undo_restores_clean_files_exactly` proves this using only the CSV, so the answer key is complete.
- **One stream per problem:** each QI code draws from `named_stream(seed, "mess.QI-xx")`. Changing one rate leaves every other problem's records identical (tested by changing the QI-06 rate).
- **Recoverable dates:** each source writes non-ISO dates in one documented convention (`02` §1.7); a test parses every injected date back by rule.
- **No accidental collisions:** a name variant that would equal another customer's real name is rejected and re-drawn, and rejections are reported (0 on the project seed). Known, deliberate ambiguity remains: the LA-1 pair differ only in legal form, so any variant that drops the suffix makes them indistinguishable by name.
- **Where files go:** the single generators (`python -m generator.helpdesk` and the others) write clean files to `data/clean/` and `data/clean/ground_truth/` only. `generator.messiness` is the only code that writes `data/raw/` and `data/ground_truth/`, so running a single generator can never overwrite the messy files or put them out of step with `known_issues.csv` (tested in `tests/test_run.py`). `python -m generator.run` builds all three folders from scratch.

## D-016: Quality problems QI-07 to QI-11 and the planted pattern after cleaning
- **QI-07 personal data:** 25% of ticket descriptions (384) get a contact sentence. Names come from a seeded Faker instance and never use staff surnames; emails use the reserved `.example` suffix; phone numbers come only from Ofcom's drama ranges (01632 960xxx, 07700 900xxx), so no real person's details can appear. Every inserted name, email and phone number is logged as a `pii_span` entry in `known_issues.csv` with its exact text and type (579 spans: 290 names, 103 emails, 186 phone numbers), so Phase 6 masking can be scored for precision and recall. Undo ignores these entries.
- **QI-08 missing values:** 11 renewal dates, 90 delivered dates, 61 first-response times (58 of them on closed tickets, leaving 1,437 of 1,495 closed tickets with a measurable response time) and 276 of 691 KB links (40%) are removed from the raw files only; the ground truth keeps every link.
- **QI-10 as added rows:** cancelled (121) and refunded (60) orders are added as extra orders rather than relabelling real ones, so excluding them restores the true BL5 revenue exactly (£734,394). Credit notes (9, £2,419) are negative bill rows against real bills and genuinely reduce BL2 revenue.
- **QI-11:** the 3 BL2 lines left without a telecoms account are chosen up front, on their own stream, from active customers who are not at risk, not in a look-alike pair and not the account-switch trap, so no planted fall is erased. QI-04 duplicate bills and QI-10 credit notes avoid those accounts so their counts stay exact; this is the one deliberate dependency between problems (changing the QI-11 count can move QI-04 and QI-10 bill choices, not the other way round). One removed account belongs to ACC-0076, the healthy customer that meets the BQ-06 pattern by chance; its pattern comes from tickets and shop spend, so it is unaffected. Two telecoms accounts with no CRM BL2 line are added with bills, and 5 contract end dates move by 31–110 days.
- **BL2 revenue:** clean £1,083,532; raw as exported £1,079,860; correctly cleaned (duplicates removed, credit notes applied) £1,072,853. The cleaned figure is lower than clean because QI-11 removed £53,759 of bills and added £45,499, and credit notes take off £2,419.
- **Planted pattern after cleaning:** on correctly cleaned data the BQ-06 pattern flags exactly the same 11 customers as the clean data (the 10 at-risk customers and ACC-0076). The two duplicate orders on at-risk customers (ACC-0004, ACC-0115) fall in January and February 2026, outside both comparison quarters, so they change nothing. On uncleaned data (exact-name matching only, no deduplication, cancelled orders counted, non-ISO dates dropped, telecoms unlinked) the pattern flags nobody: all 10 at-risk customers are missed, because ticket counts split across name variants never reach the threshold and the telecoms signal cannot be linked at all.

## D-017: Ingestion (Layer 1, step 2.1)
- **No access to answers:** pipeline code reads only `data/raw/`, `knowledge_base/*.md` and `config/pipeline.yaml`. It never reads `data/ground_truth/`, `data/clean/`, `knowledge_base/_meta.yaml`, the generator's config or any generator module. `tests/test_ingest.py` scans `pipeline/` for those names and fails if one appears, so every Phase 2 score against the answer key is honest.
- **What ingestion rejects:** only rows whose structure cannot be read: a CSV row with the wrong number of values, an API record that is not valid JSON or lacks a required field, a KB file without readable front matter. These go to `data/staging/rejected_rows.csv` with a reason. A missing or unexpected column, or a missing `# SYNTHETIC DATA` marker, stops ingestion with a clear error, because the whole file is then untrustworthy. Quality problems (non-ISO dates, invalid priorities, name variants, odd contract values, cancelled orders) pass through unchanged for validation in step 2.2. On the current data, 0 rows are rejected.
- **Text only, with lineage:** every value is kept as the text that was exported (Excel cells as displayed; JSON numbers as their literal text, e.g. `155.0`). Each row carries `_source_system`, `_source_file`, `_source_row` (the file line or Excel row; the order ID for the API, plus `_source_page`) and `_ingested_at`, fixed at the as-of moment 2026-10-01T00:00:00 so output is reproducible. Type conversion happens later.
- **Shop through the API only:** the connector pages through `GET /orders` until an empty page and checks the count against the API's reported total (3,228 orders, including duplicates and cancelled orders). If the API cannot be reached it stops with a message saying how to start it; there is no fallback to the JSON file.
- **Output:** `data/staging/` (git-ignored), one UTF-8 CSV per table (`crm_accounts`, `crm_contract_lines`, `helpdesk_tickets`, `telecoms_contracts`, `telecoms_bills`, `shop_orders`, `shop_order_lines`, `kb_documents`) plus `rejected_rows.csv`, written with the standard `csv` module. Two runs give byte-identical files.
